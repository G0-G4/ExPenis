## Context

См. `proposal.md` о проблеме и `specs/category-colors/spec.md` о поведении. Сейчас Category не содержит цвета ни в SQLite/Peewee, ни в DTO, ни во Flutter. `transaction_stats_screen.dart` отдельно назначает цвета по рангу в `_buildSlices` и `_buildStackedMonthlyData`; первая функция ещё и заменяет цвет хвостовых строк серым. Подсветка «Остальных» проверяет равенство цвета серому. Размер `AppTheme.chartPalette` одновременно определяет количество лидеров через `topKeysByTotal`.

Категории уже загружаются в память аналитики при открытии и смене периода. Редактор загружает категорию по ID и сохраняет её через существующий PUT. В backend `CategoryCreateRequest` используется для POST и PUT; `get_category_by_id` пока не ограничивает запрос пользователем. Стандартные категории создаются через отдельный bulk-путь, который также нужно охватить.

## Goals / Non-Goals

**Goals:**
- Единый серверный источник цвета и одинаковое отображение на устройствах при очередной загрузке данных.
- Явный контракт совместимого обновления и миграция существующей базы без изменения исторических операций.
- Отделение цвета категории от выбора лидеров и агрегирования хвоста.

**Non-Goals:**
- Отдельный сервис настроек, дисковый кэш цветов, realtime, произвольный RGB-picker, новые зависимости.
- Изменение остальных экранов для отображения индивидуального цвета, пересмотр фильтрации или лимитов графиков, релиз/деплой в рамках этого change.

## Decisions

### 1. Цвет является полем Category и хранится как `#RRGGBB`

Добавить непустое поле `color` в Category и обязательное поле в CategoryDto. В API использовать канонические значения `#RRGGBB` из фиксированной палитры из 32 уникальных цветов; Flutter преобразует их в непрозрачный Color. Хранение самого значения позволяет сохранять выбранный цвет независимо от порядка палитры. Альтернативы: индекс палитры зависит от её перестановок, локальная настройка не синхронизирует устройства.

Задать одинаковые упорядоченные 32 значения на backend и во Flutter. Сохранить смысловые income/expense токены; серый `chartOtherColor` исключить из палитры. Конкретные оттенки выбрать при реализации с визуальной проверкой на обеих темах; фиксированные значения в SQL-миграции, backend и Flutter должны совпадать, что проверяется тестом согласованности. Два статических представления небольшой палитры позволяют обойтись существующим API, не добавляя запрос за настройками палитры.

### 2. Назначение выполняется на сервере один раз

Добавить следующую номерную SQL-миграцию (на этой базе — `008_category_colors.sql`), не меняя старые миграции. Добавление NOT NULL поля с допустимым временным default и заполнение всех существующих записей выполняются в миграции. Для заполнения упорядочить категории каждого пользователя по ID, назначить цвета по порядку палитры и повторять после 32. До повторения используются все свободные цвета; доходы и расходы составляют один пул пользователя. SQL поддерживает такое заполнение через нумерацию строк внутри пользователя; тестировать на непустой базе, а не только на пустой fixture.

В core service выбирать первый ещё не использованный цвет в порядке палитры среди всех категорий пользователя; после исчерпания выбирать наименее используемый, разрешая повторы. Выбор и вставку выполнять атомарно с корректной сериализацией SQLite-записей, чтобы параллельное создание не занимало один свободный цвет дважды. Создание стандартных категорий должно использовать тот же алгоритм с учётом всего создаваемого набора. Не назначать цвет в DTO-конвертерах или на каждом чтении. На поле цвета не вводить UNIQUE: ручные и послепалитровые повторы разрешены.

Альтернативы: случайный выбор усложняет проверку и не даёт преимуществ; хеш ID может повторять цвета при наличии свободных; назначение из текущих транзакций повторяет исходную ошибку.

### 3. Расширяется существующий PUT с сохранением совместимости

Создание в UI остаётся автоматическим; POST не требует нового поля. Отделить update DTO от create DTO: имя и тип сохраняют существующую семантику, `color` можно не присылать. Для PUT различать отсутствие поля и явно переданный null: отсутствие сохраняет текущий цвет, null или неподдерживаемое значение дают 422 до любых записей. Валидные значения входят в фиксированную палитру. GET/list/POST/PUT возвращают сохранённый цвет. Старые клиенты игнорируют дополнительное поле ответа и продолжают сохранять имя/тип без потери цвета.

Проверить `user_id` в затронутых чтении/обновлении через core service; чужая и несуществующая категория дают 404. Бизнес-логику назначения/изменения хранить в core service, обработчики оставить тонкими. Для одновременного ручного изменения с разных устройств использовать существующую семантику последней успешной записи; при отправке редактором неизменённого цвета поле можно опустить, чтобы не затереть чужое изменение при редактировании имени. Не добавлять версионирование ресурса или отдельный endpoint цвета. Backend version увеличить при изменении контракта, OpenAPI обновить через `just openapi`.

### 4. Редактор сохраняет цвет вместе с категорией

В существующем редакторе добавить компактную сетку из 32 образцов, начальное выделение текущего значения, видимый маркер выбора и доступные подписи для управления без различения оттенков. Кнопка сохранения использует существующий PUT и сохраняет имя, тип и изменённый цвет единым запросом. Навигация назад без сохранения не отправляет изменение. Ошибку показать существующим способом и оставить возможность повтора. Экран создания остаётся с автоматическим назначением. В остальных списках/формах индивидуальный цвет не показывать.

### 5. Графики получают цвет по category ID, а агрегация получает отдельные метаданные

Загруженный список категорий предоставляет карту `categoryId -> color` для обеих визуализаций. Формирование индивидуальной строки/сегмента/легенды использует только эту карту; сумма и позиция в рейтинге определяют размер и место, но не цвет. `_buildSlices` больше не мутирует цвета исходных строк, собирая серый синтетический Other отдельно.

Отвязать лимит от длины палитры: передавать в `topKeysByTotal` отдельный лимит лидеров 6. Сохраняется текущее исключение для единственного остатка: при 7 категориях показываются все 7, при 8+ — 6 и Other. Для подсветки Other хранить набор ID его участников или явный признак; сравнение RGB не определяет принадлежность. В подробной разбивке хвост остаётся с индивидуальными цветами, а подсветка агрегата продолжает выделять его участников. Аналогичную явную идентичность сохранять в помесячных столбиках и легендах.

Альтернатива расширить лимит вместе с палитрой делает диаграммы перегруженными и меняет поведение за пределами задачи.

### 6. Достаточно существующего жизненного цикла загрузки

Цвет приходит вместе с категориями, остаётся в памяти экрана и обновляется при следующей штатной загрузке. Не добавлять SharedPreferences-ключи, TTL, фоновые запросы или отдельный кэш. Отмена и ошибка сохранения не меняют серверное значение. Успешная запись доступна всем устройствам на следующем GET; уже открытый экран не обязан обновляться мгновенно.

## Risks / Trade-offs

- [32 цвета не всегда легко различить, особенно на маленьких сегментах] → сохранить подписи, легенду, выделение и суммы; проверить палитру на светлой и тёмной темах, выбор обозначать также маркером.
- [SQL, Python и Dart могут разойтись по палитре] → фиксированные канонические значения и проверка согласованности всех трёх представлений.
- [Bulk-создание, старый клиент или параллельная вставка обходят назначение] → отдельные тесты стандартных категорий, совместимого PUT и атомарного назначения.
- [Изменение поля цвета может потеряться при одновременном ручном редактировании] → последняя успешная запись побеждает; обычное обновление без изменения цвета опускает поле. Полное разрешение конфликтов вне объёма.
- [После обновления бэкенда старый UI ещё назначает цвета по рангу] → backend-first rollout безопасен для API, стабильность графиков появляется после обновления клиента.
- [Переиспользование ID после удаления] → новый серверный объект получает цвет заново, отдельного локального состояния по ID нет.

## Migration Plan

1. Проверить миграцию на отдельной SQLite-базе с категориями нескольких пользователей, 32+ категориями и существующими операциями. Сделать резервную копию production DB перед фактическим применением.
2. Применить новую номерную миграцию штатным способом проекта перед запуском обновлённого backend; проверить заполнение всех цветов и неизменность связей операций.
3. Развернуть backend с совместимым API; проверить старый запрос PUT без цвета и новый запрос с цветом.
4. Обновить клиент. Проверить выбор цвета и два устройства с повторной загрузкой аналитики.
5. При откате клиента серверные цвета сохраняются. При откате backend оставить добавленный столбец; старые записи остаются доступны, но любые созданные старым backend категории необходимо проверить и переназначить перед повторным обновлением, так как старый код использует только SQL default. Восстановление резервной копии базы требуется лишь для полного отката схемы; учитывать потерю более поздних записей.
