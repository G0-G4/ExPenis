## Context

Мотивация и согласованный объём описаны в `proposal.md`, поведение — в `specs/personal-greetings/spec.md`. Backend использует FastAPI, Peewee и async SQLite; операторский CLI уже находится в `src/expenis/server/__main__.py` и поддерживает генерацию токенов. Админской роли и интерфейса нет. Пользователь определяется JWT. Flutter открывает вкладку транзакций по умолчанию и использует локальный `setState`; Dio принимает ответы 4xx без исключений, поэтому статусы нужно проверять явно.

## Goals / Non-Goals

**Goals:** хранить состояние независимо от устройства, исключить закрытие нового назначения устаревшим запросом, использовать существующие сервисный слой и CLI, обойтись без новых зависимостей и фоновых заданий.

**Non-Goals:** push-синхронизация, хранение истории назначений, обобщённая система уведомлений, административные HTTP-операции и изменение авторизации приложения.

## Decisions

### 1. Отдельная таблица текущих назначений

Добавить модель `PersonalGreeting` и следующую по номеру SQL-миграцию (сейчас последний номер 007). Таблица `personal_greetings`: уникальный `user_id` с внешним ключом на пользователя, уникальный `assignment_id` (UUID), `text`, nullable `expires_at`, nullable `dismissed_at`, `created_at`. На пользователя физически хранится не более одной строки. Каждое назначение генерирует новый UUID и сбрасывает закрытие; замена выполняется атомарно. История не сохраняется. Время хранится и сравнивается единообразно в UTC с учётом принятого SQLite/Peewee представления.

Альтернатива — поля в `users` — смешивает профиль с отдельным жизненным циклом. Таблица всех доставленных сообщений создала бы ненужную историю. UUID не переиспользуется после удаления и защищает от запоздалого закрытия.

### 2. Бизнес-правила в сервисе

Добавить `src/expenis/core/service/personal_greeting_service.py`: назначение, просмотр оператором, удаление, чтение активного сообщения и закрытие. Все пользовательские запросы явно фильтруются по `user_id`. Закрытие использует одновременно `user_id` и `assignment_id`; устаревший или чужой идентификатор не меняет данные.

Текст проверяется до записи: непустой после проверки пробелов, длина исходного текста не более 1000 Python Unicode code points; сам текст сохраняется без потери переносов и эмодзи. Дата CLI преобразуется через стандартный `zoneinfo.ZoneInfo("Europe/Moscow")` в начало следующего дня, затем в UTC. Сравнение `now < expires_at` определяет активность. Дата в прошлом или невалидный ввод отклоняются до записи; текущая дата допустима. Просмотр оператора показывает отдельно `dismissed_at` и признак истечения, чтобы состояния не терялись, если оба истинны.

Альтернатива — планировщик удаления по сроку — не нужна: фильтрация при чтении обеспечивает точную границу без фоновой службы.

### 3. Локальный операторский CLI

Добавить подкоманды к существующему запуску `uv run -m src.expenis.server`, сохранив работу запуска сервера и `token`:

```text
greeting set (--user-id ID | --username NAME | --all) --text TEXT [--expires-on YYYY-MM-DD]
greeting show (--user-id ID | --username NAME | --all)
greeting delete (--user-id ID | --username NAME | --all)
```

`--user-id` позволяет адресовать и пользователей без username. Для переносов строк shell передаёт один многострочный аргумент. Ошибки печатаются в stderr и дают ненулевой exit code. `show` выводит идентификаторы пользователя и назначения, текст, срок и состояние; отсутствие строки явно отмечается.

Для `set --all` и `delete --all` сначала валидировать ввод и зафиксировать список ID, вывести количество получателей и попросить подтверждение. Отрицательный ответ, EOF или неинтерактивный запуск без возможности подтвердить не меняют данные; обходного `--yes` в первой версии нет. Ожидание ввода не держит транзакцию. После подтверждения записи для выбранных ID меняются в одной `async with db.atomic()`; новые пользователи не добавляются в список. Если выбранный пользователь исчез между выборкой и записью, операция целиком завершается ошибкой с предложением повторить. Нулевое количество завершается без мутации. Предпросмотр и запись используют одну и ту же выборку, а не повторный запрос «все».

Альтернатива — админская роль и экран — требует отдельной модели прав; серверный доступ уже даёт владельцу достаточное средство управления.

### 4. Узкий пользовательский API

- `GET /api/me/greeting` → `200` с `{ "greeting": null }` либо `{ "greeting": { "id": "<assignment UUID>", "text": "...", "expires_at": "<UTC ISO 8601>" | null } }`.
- `POST /api/me/greeting/{assignment_id}/dismiss` → `204`, включая повторное, устаревшее, отсутствующее или чужое назначение. Невалидный UUID → стандартный `422`. Такой no-op не раскрывает чужую принадлежность.
- Обе операции требуют существующую JWT-аутентификацию; невалидная авторизация → `401`. Публичных операций назначения, операторского просмотра и удаления нет.

DTO находятся в существующем слое server, обработчики тонкие, security и описание операций включаются в генерируемый OpenAPI. Изменение контракта сопровождается повышением backend-версии в `pyproject.toml` и `just openapi`; выпуск frontend и тегирование в этот план не входят.

Альтернатива — включить сообщение в `/api/me` — связывает обновление профиля с отдельным жизненным циклом сообщения; отдельный ресурс упрощает повторную загрузку без изменения старого ответа.

### 5. Независимый блок во Flutter

Добавить immutable-модель, сервис на `BaseService` и виджет блока. Разместить блок в `TransactionScreen` после навигации по дате, перед списком; текст не зависит от выбранной даты транзакций. Загрузка сообщения независима от загрузки транзакций, без общего блокирующего spinner. Использовать токены текущей темы и существующий язык элементов управления. Текст обычный, без интерпретации ссылок или разметки; переносы и emoji сохраняются. Для длинного текста ограничить высоту блока с доступной прокруткой текста и постоянной кнопкой закрытия, чтобы не вытеснять список на малом экране.

Загрузка выполняется при первом открытии, повторном выборе вкладки транзакций, resume приложения и пользовательском refresh. Для переключения вкладки нужен небольшой явный сигнал из `HomeScreen`; текущий `PageView` сам не гарантирует повторный `initState`. Использовать `WidgetsBindingObserver` для resume, защищать async-ответы счётчиком запроса и сбрасывать состояние при смене сессии. Локальную постоянную копию текста не хранить.

Закрытие отправляет ID показанного назначения, блокирует повторные нажатия и скрывает только этот ID после успеха. Если уже загрузилось новое назначение, ответ на старое закрытие его не убирает. При ошибке закрытия сохранить текст и дать повторить; при ошибке чтения не показывать старую неподтверждённую копию, показать компактную ошибку с retry, сохранив работоспособность транзакций. Ответы 4xx проверять явно в сервисе.

Для `expires_at` установить отменяемый таймер скрытия и проверять время при resume и повторной загрузке. Отменять таймер и observer при dispose. Синхронизация между устройствами происходит на следующем чтении, без polling или push.

Альтернатива — хранение в SharedPreferences — не обеспечивает серверное закрытие и изоляцию между устройствами. Общий баннер в оболочке HomeScreen затронул бы другие вкладки, что не соответствует согласованному месту показа.

## Risks / Trade-offs

- [Другой открытый клиент показывает старый текст до обновления] → Обновлять при входе на вкладку, resume и refresh; мгновенная синхронизация исключена из объёма.
- [Запоздалый запрос закрывает новое поздравление] → Новый UUID на каждое назначение и фильтр по UUID + пользователю в UPDATE; защита от старого ответа на клиенте.
- [Массовая замена случайно стирает персональные тексты] → Явное подтверждение с числом получателей, атомарная запись и документация семантики замены; истории восстановления нет.
- [Разные представления времени SQLite и timezone-aware Python] → Единый способ сериализации UTC и тесты до, на и после границы; локальная timezone сервера не участвует.
- [1000 символов вытесняют список на телефоне] → Ограниченная высота с прокруткой, тесты узкого экрана и увеличенного текста.
- [Часы устройства расходятся с сервером] → Сервер остаётся источником истины при каждом чтении; таймер клиента лишь скрывает уже загруженный блок.

## Migration Plan

1. Добавить новую миграцию таблицы без изменения существующих миграций; проверить её на временной БД тем же механизмом, который использует `tests/conftest.py`.
2. Развернуть миграцию и backend с API/CLI раньше frontend. Старые клиенты игнорируют новые маршруты, существующие пользователи изначально не имеют сообщений.
3. Развернуть frontend, проверить назначение, отображение, закрытие и повторное назначение на двух клиентах; добавить инструкции оператору с примерами CLI.
4. При откате сначала откатить frontend и backend; новую таблицу оставить неиспользуемой. Не редактировать старые миграции и не удалять данные автоматически. Откат frontend устраняет зависимость от нового API.
